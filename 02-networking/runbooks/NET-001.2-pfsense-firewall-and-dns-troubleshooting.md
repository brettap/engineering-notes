## ##Objective and Symptoms

Document the IoT VLAN 30 incident and a repeatable investigation workflow. The Android phone received `192.168.30.104` but reported **Connected without internet**. With cellular data disabled, it initially failed to load `https://example.com`.

The Wyze camera remained accessible. This did not establish that the phone had general internet connectivity.

**Next Logical Step:** Confirm the affected client and its Wi-Fi-only symptoms, because camera accessibility does not establish phone connectivity.

## ##Intended IoT Interface Rule Order

The handoff records the following intended order, subsequently saved and applied:

| Order | Action | Source | Destination | Service |
|---|---|---|---|---|
| 1 | Pass | IoT subnets | 192.168.30.1 | TCP/UDP 53 DNS |
| 2 | Pass | Any | Any | UDP 68 → 67 DHCP |
| 3 | Block | IoT subnets | LAN subnets | IPv4 any |
| 4 | Block | IoT subnets | This Firewall (self) | IPv4 any |
| 5 | Pass | IoT subnets | Any | IPv4 any |

The session handoff describes normal interface rule processing as first matching rule in order. The DNS exception must precede the broader firewall-self block.

Rule 3 targeted **LAN subnets**. Its description referred to internal networks, but that description does not establish that Trusted, Entertainment or every other internal VLAN is blocked. This table is a session record, not a validated complete segmentation policy. IPv6 policy and testing are not recorded.

**Next Logical Step:** Review the actual block destinations before isolation testing, because the LAN-subnets rule does not establish coverage of every internal VLAN.

## ##Root Cause and Resolution

The exceptions had been moved above the blocking rules in the editing interface, but the intended changes had not been fully saved and applied. When the page was revisited, the blocking rules appeared above the exceptions again.

The rules were reordered correctly, then saved and applied. The tested phone subsequently reported internet access and loaded `https://example.com` with cellular connectivity disabled.

**Confirmed root cause:** The intended firewall rule order was not active because the earlier changes had not been saved and applied.

**Confirmed resolution:** Saving and applying the correctly ordered rules restored the tested phone's internet connectivity on October 13, 2026. Exact timestamps require device logs or Git history.

**Next Logical Step:** Preserve the working configuration and the client verification record, because the confirmed fix depends on saved and applied rule ordering.

## ##Troubleshooting Workflow — For Future Use

1. Confirm the affected client's network, address and symptoms. Disable cellular connectivity when testing Wi-Fi internet access.
2. Confirm the active interface rule order, including whether Save and Apply Changes completed. Review the actual destinations rather than relying on rule descriptions.
3. Inspect resolver status, TCP/UDP listeners, configured interfaces and the client subnet access entry.
4. Distinguish a firewall-side lookup from a client-side test.
5. Capture the relevant VLAN interface. For the recorded phone investigation, the interface was `mvneta1.30` and the host filter was `192.168.30.104`. Reconfirm the current client address before reusing the filter.
6. Correlate client requests, visible replies and relevant firewall logs. Record what the capture establishes and what remains uncertain.
7. Before any new remediation, export the working configuration and preserve management access. Any configuration change is separate from this documentation task.
8. After an approved correction, verify the active configuration and retest from the affected client.

Avoid disabling broad firewall rules merely to prove connectivity. Check rule order before modifying resolver services.

**Next Logical Step:** Use this workflow for a future affected-client investigation, because service status alone cannot establish the complete client traffic path.
