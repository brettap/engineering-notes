# SAM-007.1 — TechWorks Client Automation Troubleshooting

**System:** TechWorks domain lab  
**Module:** SAM-007.1  
**Completed:** 2026-10-06  
**Status:** Remote management restored; scheduled task execution verified on all three clients  
**Related module:** SAM-007 — Configuring network user storage

## Synopsis

Investigated inconsistent execution of `TechWorks-UserSimulation` on TW-CL00, TW-CL01, and TW-CL02. TW-CL01 and TW-CL02 previously reported `2147946720 / 0x800710E0`; TW-CL00 succeeded. During investigation, stopped VMware guests and an incorrect automatic bridge selection interrupted domain-network connectivity and WinRM access.

The VMware bridge was corrected to the physical Intel I211 Ethernet adapter, DNS resolution and TCP 5985 connectivity were verified, and all three scheduled tasks subsequently returned `0`. The earlier task error could not be reproduced after VM availability and networking were corrected. No speculative task-security change was made.

## Objective

- Restore reliable administration of all three TechWorks clients.
- Compare scheduled task configuration and execution results.
- Identify confirmed infrastructure faults without assigning an unsupported cause to the earlier task error.
- Record successful verification and practical prevention follow-ups.

## Initial Problem

TW-CL00 completed the automation task successfully. TW-CL01 and TW-CL02 reported decimal `2147946720`, hexadecimal `0x800710E0`, associated with “The operator or administrator has refused the request.” This result identified a failed task request but did not establish its underlying cause.

During troubleshooting, remote administration became unavailable. The guests had stopped; after restart, they received addresses outside the intended LAN. AD/DNS-based administration expected `192.168.1.148–150`, while the guests were on `172.29.x.x`.

## Investigation/Troubleshooting

1. **Check guest availability.** Confirmed that the VMware clients had stopped and restarted them so that guest-side checks could proceed.
2. **Compare host and guest networking.** The host physical Ethernet used `192.168.1.103`; Hyper-V vEthernet Default Switch used `172.29.80.1`. Restarted clients received `172.29.x.x` addresses from `172.29.80.1`.
3. **Inspect VMware bridging.** VMware Bridged (Automatic) had selected the Hyper-V Default Switch instead of the physical LAN adapter. Corrected the bridge selection to Intel I211 Ethernet.
4. **Recheck DNS.** AD DNS ultimately resolved TW-CL00 to `.148`, TW-CL01 to `.149`, and TW-CL02 to `.150` on `192.168.1.x`. `Clear-DnsClientCache` was used on the administration PC and DC to discard local cached answers before retesting.
5. **Validate remote-management prerequisites.** TCP 5985 tested successfully on all three clients. WinRM was `Running` with startup mode `Automatic`; client network profiles were `DomainAuthenticated`.
6. **Compare task definitions and results.** Retrieved task principal, action, settings, state, and last-run information remotely. All principals were `SYSTEM / ServiceAccount / Highest`; all tasks were `Ready`, with last result `0`.
7. **Repeat execution manually.** The final manual invocation produced new last-run timestamps at `17:58:26/27` on 2026-10-06 and result `0` on every client.

The Command Reference provides reusable syntax. Where the exact historical command was not retained, examples are identified as verification equivalents rather than a verbatim execution transcript.

## Root Cause/Findings

**Confirmed remote-management fault:** stopped guests prevented access, and VMware's automatic bridge selection subsequently placed restarted clients on the Hyper-V Default Switch network. Their actual addresses no longer matched the LAN addresses expected by AD/DNS-based administration.

**Earlier scheduled task error:** the precise cause of `0x800710E0` remains unconfirmed. The condition was no longer reproducible after VM availability and network connectivity were corrected. Successful later execution supports recovery; it does not prove that the bridge selection directly generated the earlier scheduler error.

## Lessons Learned

- Verify VM power state before diagnosing guest services or task permissions.
- On hosts with multiple physical and virtual adapters, explicitly select the intended VMware bridge adapter.
- Compare actual guest addresses with DNS answers; a correct-looking hostname can resolve to an address the guest no longer owns.
- DNS cache clearing affects the local resolver cache on the machine where it runs. It does not edit AD DNS records or clear the DNS Server service cache.
- A successful TCP 5985 check establishes port reachability. Successful `Invoke-Command` adds evidence that remoting and authentication work.
- Compare task definitions with a working peer before changing security settings.
- Preserve uncertainty when a failure cannot be reproduced. Document the observed recovery without manufacturing a root cause.
- Check new last-run timestamps after manual starts so that an older success result is not mistaken for the new run.

## Command Reference

Run local diagnostic commands on the machine being inspected. Run remoting blocks from the authorized administration PC/DC with an account permitted to administer the clients. The commands below are documentation; they were not executed against the lab while preparing this document.

### 1. Inspect addresses and adapters

Reusable equivalents for the network investigation:

```powershell
Get-NetAdapter | Select-Object Name, InterfaceDescription, Status, MacAddress
Get-NetIPConfiguration
ipconfig /all
```

- `Get-NetAdapter` inventories adapters. `Name` identifies the Windows interface; `InterfaceDescription` helps distinguish Intel I211 physical Ethernet from Hyper-V virtual adapters; `Status` and `MacAddress` support link and reservation checks.
- `Get-NetIPConfiguration` shows interface IP, gateway, and DNS configuration. Run it on the host and guests to compare their networks.
- `ipconfig /all` prints detailed interface configuration, including DHCP server, lease, DNS server, and physical address information. `/all` requests the full report and helps identify the `172.29.80.1` address-assignment source.
- These commands inspect Windows networking. VMware bridge selection was corrected in VMware's network configuration, not by these cmdlets.

### 2. Check name resolution and clear local cache

```powershell
Resolve-DnsName -Name TW-CL00 -Type A
Resolve-DnsName -Name TW-CL01 -Type A
Resolve-DnsName -Name TW-CL02 -Type A
Clear-DnsClientCache
```

- `Resolve-DnsName` queries name resolution; `-Name` supplies the client name and `-Type A` requests IPv4 records. These are reusable verification examples. If targeting AD DNS explicitly, add `-Server <AD-DNS-IP>` after replacing the placeholder with the actual server address.
- `Clear-DnsClientCache` takes no required parameters and clears the local DNS client cache. It was used on both PC and DC before retesting. Run it separately on each machine whose local cache must be cleared. See [Microsoft's DNS cache reference](https://learn.microsoft.com/en-us/powershell/module/dnsclient/clear-dnsclientcache).

### 3. Test WinRM TCP reachability

Recorded command pattern:

```powershell
"TW-CL00","TW-CL01","TW-CL02" | ForEach-Object {
    Test-NetConnection $_ -Port 5985 |
        Select-Object ComputerName, RemoteAddress, TcpTestSucceeded
}
```

- The comma-separated names form an array; the pipeline passes each name to `ForEach-Object`.
- `$_` represents the current name. It is supplied positionally to `Test-NetConnection` as the target computer.
- `-Port 5985` requests a TCP connection test to the WinRM HTTP port. `TcpTestSucceeded=True` was obtained for all three clients.
- `Select-Object` retains the target, resolved address, and outcome to make wrong-address and port failures visible. A port test does not by itself validate WinRM authentication. See [Microsoft's Test-NetConnection reference](https://learn.microsoft.com/en-us/powershell/module/nettcpip/test-netconnection).

### 4. Inspect WinRM and the network profile

Reusable verification equivalent; run locally if remoting is unavailable:

```powershell
Get-Service -Name WinRM
Get-CimInstance -ClassName Win32_Service -Filter "Name='WinRM'" |
    Select-Object Name, State, StartMode
Get-NetConnectionProfile |
    Select-Object InterfaceAlias, NetworkCategory
```

- `Get-Service -Name WinRM` checks the named service's current status.
- `Get-CimInstance -ClassName Win32_Service` reads service configuration; `-Filter` restricts the query to WinRM. `StartMode` confirms `Auto` (Automatic) rather than inferring startup behavior from current running state.
- `Get-NetConnectionProfile` reports interface network classification; `NetworkCategory=DomainAuthenticated` was observed on the clients.
- These are inspection commands; they do not start services or change firewall/network profiles.

### 5. Compare scheduled tasks remotely

Recorded comparison pattern:

```powershell
Invoke-Command -ComputerName TW-CL00,TW-CL01,TW-CL02 -ScriptBlock {
    $TaskName = 'TechWorks-UserSimulation'
    $Task = Get-ScheduledTask -TaskName $TaskName
    $Info = Get-ScheduledTaskInfo -TaskName $TaskName

    [PSCustomObject]@{
        Computer       = $env:COMPUTERNAME
        TaskName       = $Task.TaskName
        State          = $Task.State
        LastRunTime    = $Info.LastRunTime
        LastTaskResult = $Info.LastTaskResult
        ResultHex      = ('0x{0:X8}' -f [uint32]$Info.LastTaskResult)
        UserId         = $Task.Principal.UserId
        LogonType      = $Task.Principal.LogonType
        RunLevel       = $Task.Principal.RunLevel
        Execute        = $Task.Actions.Execute
        Arguments      = $Task.Actions.Arguments
        WorkingDir     = $Task.Actions.WorkingDirectory
        StartWhenAvail = $Task.Settings.StartWhenAvailable
        RunOnBattery   = -not $Task.Settings.DisallowStartIfOnBatteries
        StopOnBattery  = $Task.Settings.StopIfGoingOnBatteries
    }
} | Format-List
```

- `Invoke-Command -ComputerName` targets all three clients; `-ScriptBlock { ... }` executes the enclosed code on each remote machine.
- `$env:COMPUTERNAME` labels results with the guest executing the block. Remoting may also add `PSComputerName` and `RunspaceId`; the latter identifies the remote runspace, not task success.
- `Get-ScheduledTask -TaskName` reads the task definition, including principal, action, state, and settings.
- `Get-ScheduledTaskInfo -TaskName` reads last-run information, including timestamp and result. If the task is in a non-root folder, supply its actual `-TaskPath` consistently to the task cmdlets. See [Microsoft's last-run information reference](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/get-scheduledtaskinfo).
- `[PSCustomObject]@{ ... }` builds a consistent report with named fields. Variables store the definition and runtime information for reuse.
- `('0x{0:X8}' -f [uint32]$Info.LastTaskResult)` converts the result to unsigned 32-bit form and formats it as eight hexadecimal digits. This made decimal `2147946720` comparable with `0x800710E0`.
- `-not` inverts `DisallowStartIfOnBatteries` to show the easier-to-read `RunOnBattery` value.
- `Format-List` displays every report property vertically. Use formatting at the end of the pipeline so the underlying objects remain available for processing beforehand.

### 6. Start the existing tasks and verify the new runs

Reusable equivalent for the final manual invocation; exact historical start syntax was not retained:

```powershell
Invoke-Command -ComputerName TW-CL00,TW-CL01,TW-CL02 -ScriptBlock {
    Start-ScheduledTask -TaskName 'TechWorks-UserSimulation'
}
```

After the runs finish, collect their current state and last-run results:

```powershell
Invoke-Command -ComputerName TW-CL00,TW-CL01,TW-CL02 -ScriptBlock {
    $Task = Get-ScheduledTask -TaskName 'TechWorks-UserSimulation'
    $Info = Get-ScheduledTaskInfo -TaskName 'TechWorks-UserSimulation'
    [PSCustomObject]@{
        Computer       = $env:COMPUTERNAME
        State          = $Task.State
        LastRunTime    = $Info.LastRunTime
        LastTaskResult = $Info.LastTaskResult
    }
} | Format-Table -AutoSize
```

- `Start-ScheduledTask -TaskName` requests execution of the existing registered task under its configured principal. It does not recreate the task or replace its security configuration.
- Starting is asynchronous: the command returning does not prove completion. Requery until the task has completed and `LastRunTime` reflects the new invocation; compare the resulting `LastTaskResult` with `0`.
- `Format-Table -AutoSize` presents the multi-client results compactly with fitted columns. The final captured timestamps were `17:58:26`, `17:58:27`, and `17:58:27` on 2026-10-06.

### 7. Understand the task action

Configured action, shown with consistent quotation for readability:

```powershell
powershell.exe -NoProfile -File "C:\TechWorks\UserSimulation\Invoke-UserSimulation.ps1"
```

- `powershell.exe` launches Windows PowerShell.
- `-NoProfile` skips PowerShell profile scripts, reducing dependence on interactive-user customization.
- `-File` selects the script to execute. Quotes preserve the path as one argument; this particular path contains no spaces and also worked unquoted.
- Task Scheduler supplies `SYSTEM / ServiceAccount / Highest` through the task principal. Those are task settings, not parameters in the action above. Running this command interactively would use the caller's context instead.
- A blank working directory means the script should not depend on an assumed current folder; absolute paths or paths derived from the script location are suitable for future script review. This was not established as a fault in this module.
