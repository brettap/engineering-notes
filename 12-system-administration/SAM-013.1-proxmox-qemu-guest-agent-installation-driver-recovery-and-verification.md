## Synopsis and Evidence Boundaries

The supplied recovery record describes two separate obstacles: IDE1 was configured but initially absent from the running VM, and the Windows VirtIO serial device had a driver error. A controlled shutdown and cold start exposed the optical drive. The VirtIO ISO `virtio-win-0.1.285` was then available as `E:`. The QEMU Guest Agent MSI was `E:\guest-agent\qemu-ga-x86_64.msi`.

The Windows QEMU-GA service was Running with Automatic startup, but the Proxmox command `qm agent 210 ping` initially failed. Installing the Windows Server 2025 x64 VirtIO serial driver resolved the `PCI VEN_1AF4&DEV_1003` device error. Its device status became OK, and `qm agent 210 network-get-interfaces` succeeded, returning `192.168.1.60/24` and MAC `BC:24:11:FE:99:E5`.

No successful repeat ping output, raw installer output, replication output, reboot-persistence test, or post-maintenance domain-health results were supplied. These must not be inferred from the successful interface query. The separate `PCI VEN_1AF4&DEV_1002` balloon device error remains unresolved.

**Next Logical Step:** Separate host configuration, guest service, and guest driver checks, because each provides different evidence about the communication path.

## Guest-Agent Installation and Service Verification

Inside **Windows**, check the media and run the MSI if installation is required:

## VirtIO Serial Driver Diagnosis and Recovery

Inside **Windows**, inspect present problem devices and the specific serial hardware ID:

```powershell
Get-PnpDevice -PresentOnly | Where-Object Status -ne 'OK' |
    Select-Object Status, Class, FriendlyName, InstanceId
Get-PnpDevice -PresentOnly |
    Where-Object InstanceId -like 'PCI\VEN_1AF4&DEV_1003*' |
    Select-Object Status, Class, FriendlyName, InstanceId
```

Device Manager → device Properties → Details → Hardware Ids provides an interactive alternative. The observed error identified `PCI VEN_1AF4&DEV_1003`, the VirtIO serial device. A specific Windows problem code was not supplied; do not invent one.

The following **recorded successful repair command** was run elevated inside Windows:

```powershell
pnputil.exe /add-driver "E:\vioserial\2k25\amd64\vioser.inf" /install
```

Repeat the targeted `Get-PnpDevice` query or inspect Device Manager afterward. The recorded serial device status became **OK**. Microsoft documents `/add-driver ... /install` as adding the package and installing it on matching devices: [PnPUtil](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/pnputil). Retain command output and any restart requirement during future execution; staging alone must not be mistaken for a healthy bound device.

Use the matching Server 2025 x64 driver from the approved media. Do not install every INF recursively, remove unrelated drivers, or alter storage/network controllers to fix this serial-device fault. If a restart is requested, use another approved maintenance window and repeat the domain-health gate.

## Preventive Recommendations and References

- Include the approved QEMU-GA MSI and OS/architecture-matched VirtIO serial driver in the Windows VM build checklist. Validate both device health and a host agent request before handover.
- Record ISO version, guest OS, driver package/version, VMID, and verification results. Verify new media through the approved source before future upgrades.
- Distinguish current and pending hardware state. Schedule a graceful full shutdown/start when required, with alternate DC availability verified first.
- Retain Start at boot as the existing setting; test host boot ordering and DC service readiness separately rather than assuming autostart proves readiness.
- Repeat service, device, host-agent, and AD checks after an approved reboot or driver upgrade. Preserve real output and timestamps without credentials or tokens.
- Track the balloon error until independently resolved and verified. Review backup/guest-agent integration separately; an interface query is not a backup test.

Technical references: [QEMU guest-agent architecture](https://wiki.qemu.org/index.php/Features/GuestAgent) describes the separate agent channel; [Microsoft PnPUtil](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/pnputil) documents targeted driver installation. Neither source verifies the TechWorks execution results, which come from the supplied recovery account.
