# SAM-001.1 — Centralized Linux Patch Management: Ansible Implementation

**Environment:** TechWorks Lab  
**Control Node:** `ubuntu-devops01`  
**Managed Nodes:** `devops02`, `locator01`  
**Automation:** Ansible Core 2.16.3  
**Patch Manager:** APT  
**Reboot Scheduler:** systemd transient timers  
**Maintenance Window:** 03:00 local server time  
**Status:** Implementation successful; `locator01` post-reboot validation pending

---

## 1. Objective

SAM-001.1 replaces the original host-local cron-based patching approach from SAM-001 with centralized Ansible patch management.

The design separates the maintenance lifecycle into distinct operations:

```text
Inventory
   ↓
SSH Connectivity
   ↓
Privilege Escalation
   ↓
Repository Health
   ↓
Package Discovery
   ↓
Package Installation
   ↓
Reboot Detection
   ↓
Maintenance-Window Scheduling
   ↓
Post-Reboot Validation
   ↓
Prometheus/Grafana Observability
```

The primary operational principle is:

> **Patching and rebooting are separate maintenance events.**

An available update can be installed without immediately interrupting a workload. When Linux reports that a reboot is required, Ansible schedules the reboot for the approved maintenance window.

```bash
ansible linux_servers -i inventory.ini -m command -a "sudo -n id"
```

Results differed between servers.

`devops02` reported that a password was required.

`locator01` reported interactive authentication was required.

```bash
ansible devops02 -i inventory.ini -b -K -m command -a "id"
```

Successful result:

```text

```

This established that:

```text
-b  → use privilege escalation
-K  → prompt for remote sudo/become password
```

The **BECOME password is the remote Linux account's sudo password**, not the SSH private-key passphrase.

# 5. Troubleshooting — `sudo-rs` Breaks Ansible Become

## Symptom

On `locator01`:

```bash
ansible locator01 -i inventory.ini -b -K -m command -a "id"
```

failed with:

```text
Timeout waiting for privilege escalation prompt
```

However, interactive sudo worked:

```bash
sudo -k
sudo id
```

and successfully returned:

```text
uid=0(root) gid=0(root) groups=0(root)
```

This proved:

- account authentication worked;
- the password was valid;
- sudo authorization worked;
- the failure was specific to Ansible's privilege-escalation interaction.

## Diagnostic escalation

Verbose Ansible execution:

```bash
ansible locator01 -i inventory.ini -b -K -m command -a "id" -vvv
```

showed Ansible successfully completing SSH transport, Python discovery and module transfer before stalling at the sudo prompt.

The sudo implementation was inspected:

```bash
sudo --version | head -20
```

Result:

```text
sudo-rs 0.2.13-0ubuntu1.2
```

Further inspection:

```bash
command -v sudo
readlink -f /usr/bin/sudo
update-alternatives --display sudo
```

revealed that `/usr/bin/sudo` ultimately resolved to the Rust implementation:

```text
/usr/lib/cargo/bin/sudo
```

Traditional sudo remained installed as:

```text
/usr/bin/sudo.ws
```

## Root cause

Ansible supplied a custom privilege-escalation prompt.

`sudo-rs` transformed/wrapped that prompt in a way that Ansible 2.16.3 did not recognize.

The authentication mechanism itself was functional; **prompt compatibility was not**.

## Remediation

```bash
sudo update-alternatives --config sudo
```

Traditional sudo was selected:

```text
/usr/bin/sudo.ws
```

Verification:

```bash
readlink -f /usr/bin/sudo
```

Result:

```text
/usr/bin/sudo.ws
```

Ansible privilege escalation subsequently worked.

### Reusable decision tree

```text
Ansible ping fails
    ↓
Investigate network / SSH / key / Python

Ansible ping succeeds
but become fails
    ↓
Test sudo manually

Manual sudo fails
    ↓
Investigate account / sudoers / authentication

Manual sudo succeeds
but Ansible become fails
    ↓
Run Ansible -vvv

Privilege prompt timeout
    ↓
Inspect sudo implementation
    ↓
sudo --version
readlink -f /usr/bin/sudo
update-alternatives --display sudo
```

# 6. Patch Playbook

Current `patch-linux.yml`:

```yaml
---
- name: Patch TechWorks Linux servers
  hosts: linux_servers
  become: true

  vars:
    allow_reboot: false
    reboot_time: "03:00"

  tasks:
    - name: Display host being patched
      ansible.builtin.debug:
        msg: "Beginning patch cycle for {{ inventory_hostname }}"

    - name: Record running kernel before patching
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_before
      changed_when: false

    - name: Update APT package cache
      ansible.builtin.apt:
        update_cache: true
        cache_valid_time: 3600

    - name: Check available package upgrades
      ansible.builtin.command:
        cmd: apt list --upgradable
      register: available_updates
      changed_when: false

    - name: Display available package upgrades
      ansible.builtin.debug:
        var: available_updates.stdout_lines

    - name: Install available package upgrades
      ansible.builtin.apt:
        upgrade: dist

    - name: Check whether reboot is required
      ansible.builtin.stat:
        path: /var/run/reboot-required
      register: reboot_required

    - name: Report reboot status
      ansible.builtin.debug:
        msg: >-
          Reboot required for {{ inventory_hostname }}:
          {{ reboot_required.stat.exists }}

    - name: Check for existing scheduled patch reboot
      ansible.builtin.command:
        cmd: systemctl status techworks-patch-reboot.timer
      register: existing_reboot_timer
      changed_when: false
      failed_when: false

    - name: Schedule one-time reboot for maintenance window
      ansible.builtin.command:
        argv:
          - systemd-run
          - --unit=techworks-patch-reboot
          - "--on-calendar=*-*-* {{ reboot_time }}:00"
          - --timer-property=Persistent=false
          - /usr/bin/systemctl
          - reboot
      when:
        - reboot_required.stat.exists
        - allow_reboot | bool
        - existing_reboot_timer.rc != 0
      register: reboot_schedule
      changed_when: reboot_schedule.rc == 0

    - name: Report scheduled reboot
      ansible.builtin.debug:
        msg: >-
          {{ inventory_hostname }} requires a reboot.
          One-time reboot is scheduled for {{ reboot_time }}.
      when:
        - reboot_required.stat.exists
        - allow_reboot | bool

    - name: Record running kernel after patch cycle
      ansible.builtin.command:
        cmd: uname -r
      register: kernel_after
      changed_when: false

    - name: Display patch summary
      ansible.builtin.debug:
        msg:
          - "Host: {{ inventory_hostname }}"
          - "Kernel before: {{ kernel_before.stdout }}"
          - "Kernel after: {{ kernel_after.stdout }}"
          - "Reboot required: {{ reboot_required.stat.exists }}"
          - "Reboot authorized: {{ allow_reboot | bool }}"
```

Syntax validation:

```bash
ansible-playbook -i inventory.ini patch-linux.yml --syntax-check
```

Expected:

```text
playbook: patch-linux.yml
```

# 10. Maintenance-Window Reboot Design

The initial playbook could perform an immediate reboot.

That design was changed to support:

```text
Patch now
   ↓
Reboot required?
   ├── NO → finish
   │
   └── YES
         ↓
    Reboot authorized?
         ├── NO → report only
         │
         └── YES
               ↓
        Existing timer?
           ├── YES → retain it
           └── NO
                 ↓
        Schedule one-time 03:00 reboot
```

The timer is deliberately **transient**.

It is not a cron job and does not establish a permanent daily reboot policy.

# 12. Troubleshooting — `systemd-run` Argument Splitting

## Symptom

`locator01` successfully patched and reported:

```text
Reboot required for locator01: True
```

but timer creation failed:

```text
Failed to find executable 03:00:00:
No such file or directory
```

Ansible showed the generated process arguments:

```text
[
  "systemd-run",
  "--unit=techworks-patch-reboot",
  "--on-calendar=*-*-*",
  "03:00:00",
  ...
]
```

## Root cause

The calendar expression:

```text
*-*-* 03:00:00
```

must be passed to `systemd-run` as **one argument**.

The `cmd:` representation split it at the whitespace.

`systemd-run` therefore interpreted:

```text
03:00:00
```

as an executable.

## Remediation

The Ansible task was changed from a command string to an explicit argument vector:

```yaml
ansible.builtin.command:
  argv:
    - systemd-run
    - --unit=techworks-patch-reboot
    - "--on-calendar=*-*-* {{ reboot_time }}:00"
    - --timer-property=Persistent=false
    - /usr/bin/systemctl
    - reboot
```

This guarantees:

```text
argument → --on-calendar=*-*-* 03:00:00
```

remains a single process argument.

### Important lesson

```bash
ansible-playbook --syntax-check
```

validates playbook/YAML structure.

It **cannot prove runtime command semantics**.

A playbook can therefore be syntactically valid while still producing an invalid process invocation.

# 17. Command Reference

### `ansible-inventory`

```bash
ansible-inventory -i inventory.ini --graph
```

`-i inventory.ini` specifies the inventory file.

`--graph` displays inventory groups and host membership hierarchically.

**Why used:** Confirms Ansible is parsing the intended hosts before performing maintenance.

### `ansible ... -m ping`

```bash
ansible linux_servers -i inventory.ini -m ping
```

The Ansible `ping` module tests SSH connectivity, remote authentication and Python execution.

It is **not ICMP ping**.

**Why used:** Separates transport problems from patch-management problems.

### `-b`

```text
-b
```

Enables Ansible privilege escalation (`become`).

**Why used:** APT and system-level maintenance require root privileges.

### `-K`

```text
-K
```

Prompts for the Ansible become password.

**Why used:** Allows sudo authentication without storing the user's sudo password in the playbook.

### `-m command`

```bash
ansible locator01 -m command -a "uname -r"
```

Runs a command directly without shell interpretation.

**Why used:** Preferred for simple commands when shell features are unnecessary.

### `-m shell`

```bash
ansible locator01 -m shell -a "dpkg -l | grep -i speedtest || true"
```

Executes through a shell.

**Why used:** Required when using pipes, redirects or shell operators such as `||`.

### `-vvv`

```bash
ansible locator01 ... -vvv
```

Enables high-verbosity Ansible diagnostics.

**Why used:** Exposed where the privilege-escalation process was stalling.

### `sudo -k`

```bash
sudo -k
```

Invalidates the user's cached sudo credentials.

**Why used:** Forces the next sudo command to perform a genuine authentication test.

### `sudo id`

```bash
sudo id
```

Executes `id` as root.

**Why used:** Verifies interactive sudo authentication and privilege escalation independently of Ansible.

### `sudo --version`

```bash
sudo --version
```

Reports the active sudo implementation/version.

**Why used:** Revealed that `locator01` was using `sudo-rs`.

### `readlink -f`

```bash
readlink -f /usr/bin/sudo
```

Resolves all symbolic links to the final executable.

**Why used:** Determined which sudo implementation `/usr/bin/sudo` actually invoked.

### `update-alternatives --display`

```bash
update-alternatives --display sudo
```

Displays alternatives registered for the `sudo` command.

**Why used:** Revealed both `sudo-rs` and traditional sudo.

### `update-alternatives --config`

```bash
sudo update-alternatives --config sudo
```

Interactively selects an installed alternative.

**Why used:** Switched `locator01` from `sudo-rs` to traditional `sudo.ws`.

### `apt list --upgradable`

```bash
apt list --upgradable
```

Lists packages for which newer versions are available.

**Why used:** Provides pre-maintenance visibility into pending package changes.

### `apt-get update`

```bash
apt-get update
```

Downloads current package metadata from configured APT repositories.

It does **not** install package upgrades.

**Why used:** Verified repository health after disabling the unsupported Ookla source.

### `apt-cache policy`

```bash
apt-cache policy dnsmasq-base
```

Displays installed and candidate package versions and repository-selection information.

**Why used:** Identified Ubuntu phased deployment as the reason an update remained pending.

### `uname -r`

```bash
uname -r
```

Displays the currently running Linux kernel release.

**Why used:** Distinguishes an installed kernel update from the kernel actually running in memory.

### `/var/run/reboot-required`

Ubuntu creates this file when installed updates require a reboot.

Ansible checks it with:

```bash
ansible locator01 -m stat \
-a "path=/var/run/reboot-required"
```

**Why used:** Provides machine-readable reboot detection rather than assuming every patch cycle requires a restart.

### `systemd-run`

```bash
systemd-run \
  --unit=techworks-patch-reboot \
  --on-calendar="*-*-* 03:00:00" \
  --timer-property=Persistent=false \
  /usr/bin/systemctl reboot
```

Creates a transient systemd service and timer.

`--unit=` assigns a predictable unit name.

`--on-calendar=` defines the execution time.

`--timer-property=Persistent=false` prevents a missed timer from executing later merely because the machine was unavailable at the scheduled time.

**Why used:** Provides a one-time maintenance reboot without creating a permanent cron schedule.

### `systemctl list-timers`

```bash
systemctl list-timers techworks-patch-reboot.timer --all
```

Displays systemd timer state, including its next execution.

**Why used:** Verifies the actual maintenance-window timestamp rather than assuming scheduling succeeded.

### `timedatectl`

```bash
timedatectl
```

Displays local time, UTC time, timezone and clock synchronization state.

**Why used:** Establishes what "03:00" actually means to the managed server.

### `ansible-playbook --syntax-check`

```bash
ansible-playbook -i inventory.ini patch-linux.yml --syntax-check
```

Parses the playbook without executing it.

**Why used:** Detects YAML and Ansible structural errors before changing managed systems.

**Limitation:** It does not validate the runtime semantics of external commands, demonstrated by the initial `systemd-run` argument-splitting failure.

### `--limit`

```bash
--limit locator01
```

Restricts a playbook execution to a subset of inventory.

**Why used:** Enables canary deployment and limits blast radius during testing.

### `-e`

```bash
-e "allow_reboot=true"
```

Supplies an extra Ansible variable at runtime.

**Why used:** Explicitly authorizes maintenance-window reboot scheduling while keeping the playbook's default behavior:

```yaml
allow_reboot: false
```

This creates a fail-safe default: **reboots must be deliberately authorized.**
