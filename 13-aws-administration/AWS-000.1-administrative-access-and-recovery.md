# AWS-000.1 — Administrative Access and Recovery

## Synopsis

**Issue/need:** The new TechWorks AWS lab account needed secure administrative access and recovery paths before routine lab work. Initially, root had no MFA, there was no non-root administrator, and losing one credential or MFA device could cause a lockout.

**Intended result:** Reserve root for root-only and recovery tasks; use a protected non-root identity for normal administration; retain a separate, tested emergency administrator; and avoid long-lived access keys for console work.

**High-level steps:** Registered a virtual MFA device and a YubiKey for root, created an administrative group and primary IAM user, then created a separate emergency group and IAM user. Verified group permissions, MFA and access-key status, and a successful emergency console sign-in.

## Scope and design

This record covers AWS-000.1A through AWS-000.1D in the standalone TechWorks lab account. It records the console workflow actually performed. AWS-000.2, including budgets and cost controls, is a separate phase.

- **Root is for account ownership, recovery, and tasks that specifically require root.** Root has broad account-level power. Routine work uses `techworks-admin` to reduce exposure of the root credential.
- **Root has two independent MFA methods.** A virtual authenticator provides the normal second factor; a separately stored YubiKey provides an alternate path if the authenticator device is unavailable.
- **Administrative permissions are group-based.** The users inherit `AdministratorAccess` through their respective IAM groups. Group membership provides a clear place to review or remove each user's administrative authorization.
- **Emergency access is separate and dormant.** `techworks-emergency` belongs to its own group, has independent credentials and MFA, and is used only for a real lockout or a planned recovery test. Its group is separate from the normal administrator group so the recovery path can be reviewed and managed independently.

> **Credential rule:** Do not create root or IAM access keys merely for AWS Management Console administration. Console sign-in uses a password and MFA; access keys are programmatic credentials and were not needed in this phase.

## AWS-000.1A — Root virtual MFA

### Steps taken

1. Opened the AWS IAM dashboard and observed the root MFA recommendation on the new account. Root access-key count was zero.
2. Opened the root security credentials page and assigned a virtual MFA device using the authenticator's private enrollment flow.
3. Returned to IAM to inspect the resulting security state. The MFA QR code and seed were kept private.

### Verification and result

The root security credentials view showed **one virtual MFA device** and **zero root access keys**. A subsequent root sign-in using this first MFA method also established that the authenticator worked for login. **AWS-000.1A complete.**

## AWS-000.1B — Root backup YubiKey MFA

### Steps taken

1. From the root security credentials page, selected **Assign MFA device** and the **Passkey or security key** option for the YubiKey.
2. The initial registration attempt failed because the current root session had been created before the virtual MFA device was registered. See troubleshooting below.
3. Signed out of root, signed back in with the root password and existing virtual MFA, and repeated the security-key registration flow.
4. Inspected the root MFA device list after registration.

### Verification and result

The root security credentials view showed **two registered MFA devices**: the virtual authenticator and the YubiKey/security key. Root access keys remained **zero**. The YubiKey's registration was verified in the console; a separate root sign-in *using the YubiKey* was identified as a future recovery-path test and is **not recorded as completed here**. **AWS-000.1B registration complete.**

## AWS-000.1C — Primary non-root administrator

### Steps taken

1. In **IAM → User groups**, created `Techworks-Administrators` and attached the AWS-managed `AdministratorAccess` policy to the group.
2. In **IAM → Users**, created `techworks-admin` with AWS Management Console access and added it to `Techworks-Administrators`. No administrator policy was attached directly to the user.
3. Used an autogenerated initial console password with a required password change at first sign-in. Stored the credential securely, signed out of root, signed in as `techworks-admin`, and set a new permanent password.
4. Assigned a virtual MFA device to `techworks-admin`.
5. Reviewed the user's security credentials and the group's **Users** and **Permissions** tabs. No access key was created.

### Verification and result

The non-root console sign-in succeeded. The user showed console access, **one virtual MFA device**, and **zero access keys**. The group showed `techworks-admin` as a member and `AdministratorAccess` under Permissions, confirming the authorization chain:

```text
techworks-admin → Techworks-Administrators → AdministratorAccess
```

Normal AWS administration moved to `techworks-admin`. **AWS-000.1C complete.**

## AWS-000.1D — Break-glass administrative access

### Steps taken

1. While signed in as `techworks-admin`, created `Techworks-EmergencyAccess` under **IAM → User groups** and attached the AWS-managed `AdministratorAccess` policy. The group initially had no members.
2. Started an IAM user for `techworks-emergency` with Management Console access. Selected the **IAM user** path and added the new user to `Techworks-EmergencyAccess`, not `Techworks-Administrators`. No administrator policy was attached directly to the user.
3. Reviewed the user-creation settings. The first review screen displayed **Autogenerated** for the console password, although **Custom password** had been intended. The selection was corrected before creation. A new, unique custom password was generated and stored in KeePass. **Users must create a new password at next sign-in** was left unchecked so the emergency credential would be ready during a lockout.
4. Created the user, verified its group membership, and assigned its own virtual MFA device. No access key was created.
5. Signed completely out of `techworks-admin`, signed in through the IAM console sign-in URL as `techworks-emergency` using the stored password and virtual MFA, and opened **IAM → Users**. This was a read-only recovery test; no configuration change was made with the emergency identity.

### Verification and result

The emergency user's security view showed **one group**, **one virtual MFA device**, console password access, and **zero access keys**. The successful emergency sign-in and ability to view IAM users confirmed that the recovery identity could authenticate and access an administrative console page. The group permission path was verified as:

```text
techworks-emergency → Techworks-EmergencyAccess → AdministratorAccess
```

The emergency identity is designated for dormancy after the test. The conversation instructed signing out of it and returning to `techworks-admin`; that final sign-out/return was **not separately evidenced** in the available record. **AWS-000.1D access test complete.**

## Issues Encountered / Troubleshooting

### Second root MFA registration failed

**Symptom:** AWS rejected the first YubiKey registration attempt and required authentication with an MFA device already enabled for the root user.

**Cause:** The active root session began before the first, virtual MFA device was enrolled. Adding MFA during that session did not retroactively make the session MFA-authenticated.

**Resolution:** Signed out completely, signed back in as root with the already registered virtual MFA, then retried YubiKey enrollment. The root credentials page subsequently showed both MFA devices. The error did not establish a YubiKey hardware fault.

### Emergency password review showed the wrong source

**Symptom:** The first `techworks-emergency` review screen showed **Autogenerated** even though **Custom password** had been requested. **Require password reset** correctly showed **No**.

**Resolution:** Before creating the user, returned to the password settings, generated a new custom password in KeePass, selected **Custom password**, and kept the forced-reset option unchecked. The subsequent pre-creation review confirmed the intended settings. The password source and the forced-reset setting are separate controls; both were checked.

## Security and publication notes

- Keep the root password, admin passwords, MFA devices, and emergency credential in their intended secure locations. Store the backup YubiKey separately from the virtual authenticator device.
- The emergency identity should remain unused except for a genuine recovery event or a planned, read-only recovery test. Record future tests without exposing credentials.
- **Before adding screenshots or this document to public Git, redact AWS account IDs, ARNs, email addresses, MFA device identifiers, passwords, QR codes, MFA seeds, and other secrets.** Do not commit unredacted enrollment or password-retrieval screens. Names of the lab IAM users and groups in this document are descriptive configuration labels, not credentials.
