# AWS-000.2 — Administrative Access Foundation

## Synopsis

### Issue

The TechWorks AWS account required a secure administrative-access model for routine management while preserving separate emergency access. The account already had administrative IAM components from earlier AWS-000 work, but their configuration and authorization paths needed to be discovered, inspected, and functionally verified.

IAM Identity Center was initially considered as the preferred long-term administrative-access architecture. During configuration, AWS presented an important cost consideration: enabling the required AWS Organizations-based Identity Center configuration would move the account away from its current Free Plan arrangement and affect available free credits. Multi-Region Identity Center also introduced a customer-managed AWS KMS key and associated cost/complexity.

Because the current objective is to maintain a low-cost AWS lab, those capabilities were deliberately deferred.

### Intended Result

Establish and verify two distinct administrative paths:

```text
Routine Administration
techworks-admin
        ↓
Techworks-Administrators
        ↓
AdministratorAccess


Emergency Administration
techworks-emergency
        ↓
Techworks-EmergencyAccess
        ↓
AdministratorAccess
```

Both identities must:

- Require MFA for console authentication.
- Receive administrative authorization through IAM groups.
- Have no unnecessary long-lived access keys.
- Remain operationally separate.
- Be tested before being considered functional.

The root user remains reserved for account ownership and operations that specifically require root credentials.

### Brief Synopsis of Steps Taken

The existing IAM configuration was inspected before making changes. The `techworks-admin` and `techworks-emergency` IAM users were found to already exist, both with MFA and without access keys.

Their IAM group memberships were then inspected. `techworks-admin` was confirmed as a member of `Techworks-Administrators`, while `techworks-emergency` was associated with the separate `Techworks-EmergencyAccess` group.

The AWS-managed `AdministratorAccess` policy was inspected to understand the actual authorization granted by these groups. Its policy document grants `Allow` for all actions against all applicable resources.

IAM Identity Center and AWS Organizations were evaluated but deferred because of the current requirement to preserve the AWS Free Plan and avoid unnecessary KMS and multi-region costs.

Finally, the emergency session was terminated and a new console session was successfully established as `techworks-admin` using MFA, proving that normal administrative access works independently of the break-glass identity.

# 1. Administrative Access Objectives

The AWS account should not rely upon the root user for normal administration.

Likewise, the emergency account should not become the normal working administrator simply because it possesses administrative permissions.

The administrative identities therefore have clearly defined purposes.

| Identity | Purpose | Normal Use |
|---|---|---|
| AWS root | Account ownership and root-required operations | No |
| `techworks-admin` | Routine AWS administration | Yes |
| `techworks-emergency` | Break-glass/recovery administration | No |

This provides separation between normal operations, emergency recovery, and account ownership.

```text

techworks-emergency
```

Both identities already had console credentials configured.

The IAM user inventory showed that both users had MFA configured and neither had an AWS access key.

This meant that the required components did not need to be recreated.

```text

   ↓

```

Normal administrative work should therefore occur as:

```text
techworks-admin
```


# 5. Separation of Administrative Paths

Although both identities currently receive the same AWS-managed administrative policy, their group memberships are separate.

```text
                    AWS ACCOUNT
                         │
            ┌────────────┴────────────┐
            │                         │
     NORMAL OPERATIONS          EMERGENCY ACCESS
            │                         │
            ▼                         ▼
    techworks-admin          techworks-emergency
            │                         │
            ▼                         ▼
Techworks-Administrators   Techworks-EmergencyAccess
            │                         │
            └────────────┬────────────┘
                         │

```

This separation is intentional.

The two identities currently possess equivalent administrative capability, but they serve different operational functions.

Separate groups make it possible to later apply different policies, controls, monitoring, or restrictions to emergency access without modifying the normal administrator.

# 6. IAM Group-Based Permission Management

Permissions were assigned through IAM groups rather than directly attaching the administrative policy to each individual IAM user.

Conceptually:

```text
IAM User
   ↓
IAM Group
   ↓
IAM Policy
   ↓
Allowed AWS Actions
   ↓
AWS Resources
```

For the routine administrator:

```text
techworks-admin
        ↓
Techworks-Administrators
        ↓
AdministratorAccess
```

For emergency access:

```text
techworks-emergency
        ↓
Techworks-EmergencyAccess
        ↓
AdministratorAccess
```

An IAM group is not itself an authenticating identity or principal. It provides a mechanism for collectively assigning permissions to IAM users.

---

# 7. AdministratorAccess Policy Inspection

The AWS-managed policy attached to the administrative groups was inspected.

Policy:

```text
AdministratorAccess
```

AWS describes this policy as providing full access to AWS services and resources.

The policy document contained:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "*",
            "Resource": "*"
        }
    ]
}
```

## Policy Interpretation

### `"Effect": "Allow"`

The statement grants permissions.

### `"Action": "*"`

The wildcard permits all AWS API actions to which the policy applies.

### `"Resource": "*"`

The permissions apply to all applicable resources.

Together:

```text
Effect:   Allow
Action:   *
Resource: *
```

provide extremely broad administrative authorization.

This does **not** make an IAM administrator equivalent to the AWS account root user. Certain account-level operations remain restricted to the root identity.

---

# 8. Authentication vs. Authorization

This stage demonstrated an important IAM distinction.

## Authentication

Authentication answers:

> Who are you?

For `techworks-admin`, authentication is performed using:

```text
IAM username
      +
Password
      +
MFA
```

## Authorization

Authorization answers:

> What are you permitted to do?

For the normal administrator:

```text
techworks-admin
        ↓
Techworks-Administrators
        ↓
AdministratorAccess
        ↓
AWS administrative permissions
```

MFA therefore strengthens authentication.

The IAM policy determines authorization.

The two mechanisms solve different security problems.

---

# 9. Access Keys

Neither administrative identity currently has an AWS access key.

This is intentional.

```text
techworks-admin
Access key: NONE

techworks-emergency
Access key: NONE
```

Console administration does not require IAM access keys.

Creating long-lived programmatic credentials before they are required would unnecessarily increase the credential attack surface.

When AWS CLI or API automation is introduced later, programmatic authentication will be designed as a separate stage rather than automatically creating permanent IAM access keys.

---

# 10. IAM Identity Center Evaluation

IAM Identity Center was evaluated as a potential replacement for routine IAM-user administrative access.

The intended architecture would eventually resemble:

```text
Administrator
      ↓
IAM Identity Center
      ↓
Permission Set
      ↓
AWS Account / Role
```

This remains a desirable future direction as the TechWorks AWS environment grows.

However, the current AWS account is being intentionally maintained as a low-cost learning environment.

During the Identity Center setup process, AWS presented a warning that creating the required AWS Organization would affect the account's current Free Plan arrangement and free credits.

Because maintaining the Free Plan is currently a higher priority than implementing the full Identity Center architecture, AWS Organizations and the corresponding Identity Center organization instance were deferred.

---

# 11. Single-Region vs. Multi-Region Identity Center

The Identity Center configuration workflow presented multiple deployment choices.

These included:

```text
Multi-Region instance
Single-Region instance
Custom instance
```

The Multi-Region option also introduced a customer-managed AWS KMS key for encryption.

AWS indicated that KMS charges could apply.

At the current stage of the TechWorks lab:

- Multi-region administrative resiliency is not required.
- A customer-managed KMS key is not required for the current workload.
- Additional cost should not be introduced without an operational requirement.
- IAM Identity Center itself is currently being deferred.

Therefore:

```text
Multi-Region Identity Center: DEFERRED
Customer-managed KMS key:     DEFERRED
AWS Organizations:            DEFERRED
```

This was a deliberate architecture and cost-management decision.

# 17. Operational Rules Going Forward

Normal AWS administration should use:

```text
techworks-admin
```

The following should **not** be used for routine administration:

```text
root
techworks-emergency
```

The break-glass credentials should remain secured and unused except when the normal administrative path cannot be used or when explicitly testing the emergency-access procedure.

Programmatic access should not be enabled simply for convenience. It should be introduced when a workload, AWS CLI workflow, automation system, or infrastructure-as-code requirement justifies it.

---

# 18. Lessons Learned

AWS administration should begin with **state discovery**, not resource creation.

A useful operational workflow is:

```text
Observe
   ↓
Discover
   ↓
Understand
   ↓
Determine desired state
   ↓
Change only what is necessary
   ↓
Verify
   ↓
Document
```

This stage also demonstrated that having equivalent permissions does not mean two identities serve the same operational purpose.

`techworks-admin` and `techworks-emergency` both currently possess administrative authorization, but their roles are fundamentally different.

Finally, architectural maturity does not mean enabling every available AWS capability. AWS Organizations, Identity Center, multi-region resiliency, and customer-managed KMS keys can all be useful, but they should be deployed because requirements justify them—not simply because the console offers them.
